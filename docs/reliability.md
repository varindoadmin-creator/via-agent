# VIA Reliability

Jarvis-specific reliability detail (failure taxonomy, circuit breaker, Zoho retry policy, approval-write idempotency) is documented in `docs/jarvis-reliability-production-engineering.md` and is not repeated here. This document covers the whole system: WATI, Zoho, Supabase, and the background-job queue Phase 13 adds.

## A. Failure model

Every failure mode from Phase 13's brief section 4, and how VIA actually handles it today:

| Failure | Handling | Where |
|---|---|---|
| WATI unavailable (send fails) | `sendWatiText` returns `'failed'`/`'disabled'` rather than throwing; the caller decides whether to leave state unchanged (customer-facing pipeline) or enqueue a retry job (proactive outreach) | `lib/integrations/wati/client.ts`, `lib/proactiveActions/sendOutreach.ts` |
| Zoho unavailable | Reads retry (~2x, exponential jitter) on transient/429/5xx; writes never auto-retry — a timeout is an unknown outcome, reconciled manually | `lib/zoho/retry.ts`, `lib/jarvis/reliability/*`, `/api/jarvis/recovery` |
| Supabase unavailable | Every durable-state read/write that isn't itself the critical path (analytics events, audit logs, memory) is best-effort and never throws into the caller; critical-path writes (approval claims, action transitions) do throw, and the caller must not assume success without a confirmed row | `lib/analytics/events.ts`, `lib/proactiveActions/store.ts`, `lib/commercialApprovals/store.ts` |
| LLM unavailable / timeout | `withTimeout` bounds the whole agent run (`JARVIS_RUN_TIMEOUT_MS`, default 48s); `app/api/jarvis/chat/route.ts`'s catch-all returns a safe, reference-numbered error, never a stack trace | `lib/jarvis/reliability/timeout.ts`, `app/api/jarvis/chat/route.ts` |
| Network timeout (general) | Same `withTimeout`/circuit-breaker layer for Jarvis tool calls; `fetchWithRetry` for Zoho HTTP | `lib/jarvis/reliability/timeout.ts`, `lib/zoho/retry.ts` |
| Malformed webhook | Rejected with 400 before any processing; payload is generically parsed (`parseWatiWebhookPayload`), never assumed well-formed | `lib/integrations/wati/webhook.ts`, tested in `lib/integrations/wati/webhook.test.ts` |
| Duplicate webhook | `wati_messages.provider_message_id` uniqueness — a retried webhook is recognized and not reprocessed | `lib/integrations/wati/store.ts`, tested in `lib/integrations/wati/webhook.test.ts` |
| Outbound send failure | Never silently retried forever: the customer-facing pipeline just leaves state unchanged for the next natural interaction; proactive outreach (Phase 11) enqueues a bounded, DLQ-backed retry job (section C below) | `lib/proactiveActions/sendOutreach.ts` |
| DB contention (concurrent writers) | Optimistic concurrency (`version` column + conditional PATCH) on every durable workflow table — a losing writer gets an empty result and must reload, never a silent overwrite | `lib/proactiveActions/store.ts`, `lib/operationalIntelligence/findingStore.ts`, `lib/jobs/queue.ts` |
| Stale data | Price/customer/item facts are re-resolved immediately before any write or send, never trusted from detection/preparation time | `lib/commercialApprovals/executeCommercialDraft.ts`, `lib/proactiveActions/sendOutreach.ts` |
| Worker crash | N/A in the literal sense — there are no long-running workers; a Cloud Run instance crashing mid-request simply fails that request, and durable state (claims, versions) ensures a retry is safe, not duplicative | — |
| Partial write | Zoho-write-then-Supabase-record-failure is the one real partial-write risk; handled by marking the action `EXECUTING`/unknown and requiring manual reconciliation rather than a blind retry | `lib/jarvis/approvals/store.ts`'s `markExecutionUnknown`, `/api/jarvis/recovery` |
| Unknown write outcome | Never retried automatically — see `docs/jarvis-reliability-production-engineering.md`'s "Idempotency and unknown write outcomes" | `lib/commercialApprovals/executeCommercialDraft.ts` |
| Rate limit (from a dependency) | Classified as `RATE_LIMIT`, bounded retry for reads, circuit breaker opens on repeated failure | `lib/jarvis/reliability/errors.ts` |
| Rate limit (into VIA) | New this phase — `lib/security/rateLimit.ts` on login and Jarvis chat; the WATI webhook is deliberately NOT rate-limited (see section D) | `lib/security/rateLimit.ts` |
| Authentication failure | Session-cookie verification at the middleware layer for every non-public/non-cron route; WATI webhook has its own bearer-secret check | `middleware.ts`, `lib/integrations/wati/webhook.ts` |

## B. Service reliability tiers

`lib/reliability/tiers.ts` classifies named business functions as `CRITICAL` (inbound WATI ingestion, customer identity, pricing, order/quotation approval-write, payment status, stock workflow persistence), `IMPORTANT` (analytics, proactive findings/actions, sample workflow), or `NON_CRITICAL` (management summaries, optional enrichment). This is documentation-as-code — it does not itself change runtime behavior, but shapes how the DLQ alert (section C) and this failure-model table should be read: a `NON_CRITICAL` job accumulating in the DLQ is a backlog to clear when convenient, not a page-someone event.

## C. Durable job queue and idempotency

`lib/jobs/queue.ts` (table: `background_jobs`) is a Supabase-backed queue, not a new infrastructure dependency — claiming a job uses the same `version`-column optimistic-concurrency pattern as every other durable workflow in this codebase. It exists for exactly two concrete use cases, not as a general-purpose mechanism every subsystem is expected to adopt:

1. **`wati_send_retry`** — when `lib/proactiveActions/sendOutreach.ts` gets a transient WATI send failure (or WATI is unconfigured), it enqueues a job idempotency-keyed on `sendOutreach:{actionId}:{version}` — a repeat failure at the same action version never creates a second DLQ entry. `app/api/jobs/sweep` retries via `sendProactiveOutreach` itself, so every safety check (eligibility, opt-out, human-active) still applies on the retry, not just on the first attempt.
2. **`salesperson_assign_retry`** — when `lib/salespersonMap/sync.ts`'s Zoho PUT fails for one document, the failure is now durably retried (previously: logged and forgotten) via `retrySalespersonAssignment`.

A job handler distinguishes retryable failures (default: exponential backoff, mirroring `lib/zoho/retry.ts`'s `baseDelayMs * 2**attempt + jitter` shape) from permanent ones (`PermanentJobFailure` — a policy/validation outcome that retrying cannot fix, per brief section 5's "do not retry a validation error, permission denied, invalid customer data, or policy denial") — a permanent failure skips straight to `DEAD`, never spending its retry budget pointlessly. A `DEAD` job is visible and actionable at `/requests/wati/system-health`, never silently dropped.

**Idempotency beyond the job queue** is unchanged from before this phase and already covers every genuinely critical write: customer creation and Sales Order/quotation creation use a single-claim approval row (`lib/commercialApprovals/store.ts`); proactive-action sends use `version`-based optimistic concurrency as the send-idempotency guard (a second concurrent attempt gets a version conflict, reported as `DUPLICATE_PREVENTED`, never a second message).

## D. Webhook processing — deliberately synchronous, not rearchitected this phase

`app/api/integrations/wati/webhook/route.ts` validates (content-type, bearer secret if `WATI_WEBHOOK_SECRET` is configured, payload size), parses, and then runs the full inbound pipeline (`processInboundWatiMessage`) synchronously before returning — it does not ack-then-enqueue. This is a known, accepted gap against brief section 10's "acknowledge quickly, enqueue processing" ideal, and is **not rearchitected in this phase**: every prior phase (2 through 12) was built and tested against the synchronous path, and rearchitecting the single highest-traffic entry point into an async queue is a large, high-risk rewrite that deserves its own dedicated pass with its own eval/regression coverage, not a rider on a reliability-hardening phase. The route already bounds the whole request (`maxDuration = 30`), and every network call inside the pipeline (Zoho, WATI outbound) is itself timeout/retry-bounded, so a single slow webhook cannot hang indefinitely — it can take up to ~30 seconds, not forever. **Future migration path**: if webhook volume or latency ever demands it, the natural seam is exactly where `processInboundWatiMessage` is called today — replace that call with `enqueueJob({ jobType: 'wati_inbound_process', payload: parsed.payload, idempotencyKey: providerMessageId })` and add a handler to `app/api/jobs/sweep`, reusing the exact queue this phase already built.

**Webhook authentication**: `isAuthorizedWatiWebhook` (`lib/integrations/wati/webhook.ts`) checks a bearer token against `WATI_WEBHOOK_SECRET` using a timing-safe comparison, but — matching WATI's actual supported capability, not an invented HMAC scheme — only enforces it when the secret is configured; with no secret set, the check passes open. This is a real, disclosed risk if `WATI_WEBHOOK_SECRET` is never configured in production: **confirm `WATI_WEBHOOK_SECRET` is set in the Cloud Run environment** (this cannot be verified from the codebase). WATI has no documented HMAC-signature scheme to enforce instead; the payload-size cap and idempotent, non-destructive processing (a forged webhook can at most inject a fake inbound message, which flows through the same identity/permission checks as a real one — it cannot forge a session or bypass approval) are the other controls in place.

## E. Concurrency and races

Every race named in brief section 23 already has a specific guard: two inbound messages (webhook idempotency on `provider_message_id`), human takeover mid-composition (the `isNowHumanOwned` recheck immediately before the pipeline's one outbound send — see `lib/integrations/wati/pipeline.ts`, tested in `lib/integrations/wati/pipelineRace.test.ts`), two admins approving the same draft (single-claim approval rows), a stock response arriving twice (idempotent inquiry resolution), duplicate webhooks (as above). Phase 13 adds one more: two sweep invocations racing the same background job (the job-claim PATCH's `version`+`status=eq.PENDING` filter — only one claimer wins).
